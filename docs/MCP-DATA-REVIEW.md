## 1. Read tools — data exposure

### Method

`tests/mcp.exposure.test.js` runs **every read tool for every role** that can see it (ADMIN, PRINCIPAL, FINANCE, TEACHER,
LIBRARIAN, WARDEN, PARENT, STUDENT) against a fixture that holds everything a real student file carries: a photo, a medical
record with an emergency contact and an attachment, published marks entered by a teacher, a submitted assignment, a class
teacher and a father with phone numbers and email addresses. It reads the envelope the MCP server returns — what a model
and a chat transcript actually receive — and fails if any result, at any depth, contains:

- a tenant id, `__v`, an account id, a password, a hash, a token, an API key, a secret or an encrypted field (`*Enc`);
- the value of any configured secret (JWT, medical encryption key, WhatsApp token or app secret, AI keys);
- the student photo URL.

Behind the tools' own field lists, the MCP server strips the same keys from every result before it leaves
(`redactResultData` in `mcp/server.js`) — a backstop, tested directly in the same suite.

It also records which **personal data** each tool returned to which role. That inventory is the last column below.

### Findings

| Finding | Assessment | Action |
|---|---|---|
| `get_student_overview` could return the student photo URL, the class teacher's phone and email, internal record ids, and decrypted medical data it then discarded. | Over-exposure. | **Fixed.** Loads only the requested sections (the service now accepts `sections`); each section is an explicit field list; photo and staff contact never returned; medical returned only with `medical.read`, attachments as names only; no medical read (and no medical-disclosure audit entry) unless asked for and permitted. Tested per role. |
| `get_medical_record`, and `get_student_overview` with `include: ['medical']`, return allergies, medications, history and the emergency contact. | Legitimate for `medical.read` holders (ADMIN, WARDEN school-wide; the class teacher, the parent and the student for their own record). Every read is recorded as a medical disclosure. | None. |
| `get_dashboard` returns a phone number and email to parents. | The class teacher's contact on the parent dashboard — shown to parents on the website by design (`dashboard.service.js`). | None. |
| `get_student_overview` with `include: ['personal', 'guardians']` returns date of birth, address and guardian contacts to FINANCE and LIBRARIAN. | Consistent with the permission model: both roles hold `students.read` at ALL and see the same on the student panel. Whether a librarian *should* is a policy question. | **Role review** before go-live (MCP-PRODUCTION-READINESS.md §6). Narrowing the role narrows the assistant automatically. |
| `get_announcements` carried an `email` key. | A delivery flag (`channels.email: false`), not an address. | None. |
| `list_audit_logs` returns other people's actions. | Legitimate for `audit.read` at ALL; sensitive fields inside entries are redacted by `audit.service`. | None. |

## 2. Write tools — operation review

### How each property is enforced — for every write tool

These are properties of the one execution path, not of individual tools, so they hold for all
68 write tools:

| Property | Enforced by | Evidence |
|---|---|---|
| Authentication | The session handle, minted from the JWT-authenticated actor (website) or the Meta-signed phone number (WhatsApp); identity arguments are refused on writes. | `mcp.security.test.js` (identity, tenancy); `mcp.e2e` / `mcp.readiness.e2e` (both channels) |
| Authorization | The tool's permission against the live permission map, at call time and again at confirmation. | Role matrix probe over all 137 tools × every role + a custom role (`mcp.security`); permission removed between proposal and yes (`mcp.confirmation`) |
| Tenant isolation | The session's tenant state re-entered around every call; tenant-scoped models; a write needs a school. | Cross-school ids, tokens and routes refused (`mcp.security`, `mcp.writes`, `mcp.confirmation`) |
| Scope | `minScope: ALL` tools refuse OWN holders; OWN callers are narrowed by the services. | OWN-scope suite (`mcp.security`); teacher document deletion (`mcp.writes`) |
| Input validation | JSON Schema, `additionalProperties: false` at every level; unknown arguments refused, not dropped. | `mcp.architecture` (every object closed; no query/collection/url/update parameters) |
| Business rules | The existing EduOS services — no tool contains business logic. Where a service check can fail, 18 tools run it *before* the confirmation prompt (`prepare`). | Overpayment, invalid plan transition, stop not on route, not-your-document, recipient outside the school (`mcp.resilience`, `mcp.writes`, `mcp.writes.coverage`) |
| Confirmation | 64 of 68 writes (all HIGH/CRITICAL/DELETE/bulk/external). Server-enforced; single-use, atomically claimed, owner-bound, 10-minute tokens. | `mcp.confirmation` (valid, expired, reused, other user, other school, permission removed, simultaneous, declined) |
| Audit | Every call, every outcome, `agent.<tool>` with `via: MCP`; before/after state for the tools that can supply it. | `mcp.security` audit suite; three-way checks in `mcp.readiness.e2e` |
| Idempotency | Services (conditional updates, unique keys, skip-if-billed) plus single-use tokens. | `mcp.security` (double confirm, mark twice, duplicate invoice, generate twice) |
| Error handling | Structured error codes; no internal messages to the model; timeouts on writes report an unknown outcome and settle later. | `mcp.resilience` |

The 4 writes without confirmation are low-impact requests a person files for themselves: `create_hostel_inquiry`, `request_cocurricular`, `request_profile_edit`, `create_ticket`.
